# CONCERNS

## Overview
This document logs technical debt, known structural issues, and areas of concern within the `openwrt-passwall` codebase.

## Technical Debt & Fragile Areas
1. **Monolithic Init Script**:
   - The primary `passwall` init script handles the management for over a dozen proxy cores. Any change to the core network routing methodology must maintain backward compatibility logic for multiple overlapping frameworks (Shadowsocks vs Xray vs Sing-Box).
   - This makes debugging very complex when things go wrong.

2. **Iptables vs Nftables Fragmentations**:
   - The Makefile provides distinct selection configurations (`_Iptables_Transparent_Proxy` vs `_Nftables_Transparent_Proxy`). Supporting both legacy `iptables` flows and modern `nftables` structures creates duplicate logic areas that need independent validation when routing bugs emerge.
   - Nftables migration is an ongoing OpenWrt standard, but legacy iptables still require heavy maintenance.

3. **Implicit Dependency Behavior**:
   - Package builds assume `passwall-packages` (the actual underlying binaries) is populated in the feed. When these fail to compile or upstream URLs die (such as recent SourceForge connection issues), the app components break because of implicit environmental assumptions.
   - Requires robust fallback and error handling.

## Security Configurations
- The router manipulates sensitive network capabilities (DNS resolution overrides, transparent interceptions). If rules generated by the scripts apply overly broad `0.0.0.0/0` logic improperly, they could create internal loopbacks or bypass intended firewall isolations (particularly for incoming WAN traffic vs standard LAN NAT).

## Performance
- Loading massive GFWList sizes directly into `dnsmasq` or raw `ipset` rules can cause router memory saturation on low-end hardware (e.g., devices with <128MB RAM). Proper memory constraint behaviors need to be monitored in future updates, specifically looking for `OOM` kills.
